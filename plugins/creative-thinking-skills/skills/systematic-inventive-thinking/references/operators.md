# The Five SIT Operators — Recipes, Prompts, and Checks

Use one operator at a time. Each takes the listed system and its environment as the only building material. The virtual product it yields must be infeasible at first — that tension is the point.

## 1. Subtraction — remove an essential component

**Recipe:** List components, pick one that seems essential, remove it entirely (not its function, the component itself). Keep the system otherwise unchanged.

**Prompt:** "If this component did not exist, how would the system still deliver its core benefit?"

**Example:** Onboarding flow without the welcome email. Virtual product: no welcome email, ever. To make it work, the job it did must be absorbed elsewhere.

**Check:** Is the removed component truly essential? If removal changes nothing, it was not essential — pick another.

## 2. Multiplication — copy a component and change it

**Recipe:** Choose a component, copy it (same type, not just more of the same instance), then change a key attribute (time, place, performer, form). Keep copies distinct.

**Prompt:** "If we had two of this, differing in one meaningful way, what new value appears between them?"

**Example:** Two onboarding checklists — one before first value, one after — with different owners. Do not simply duplicate; the change must create a new relation.

**Check:** Are the copies different in kind, not just quantity? Quantity alone rarely yields a new benefit.

## 3. Division — divide and reorganize

**Recipe:** Split a product, process, or set into parts along a non-obvious boundary, then reorganize the parts in space, time, or responsibility.

**Prompt:** "If we cut along a different seam and rearranged the pieces, what arrangement would make a hidden benefit visible?"

**Example:** Split onboarding into invite-carried intent (before first open) and in-product checklist (after). Rearrange who owns each part.

**Check:** Is the cut non-obvious? Cutting where everyone already cuts produces the same design.

## 4. Task Unification — assign a new task to an existing component

**Recipe:** Pick an existing component or nearby environmental element and give it a new task that another component currently does — then remove the other component from that task.

**Prompt:** "Which existing element could do this job instead, so we no longer need the current performer?"

**Example:** The invite itself carries onboarding context, so the welcome email has no job. The teammate's shared artifact becomes the orientation sheet.

**Check:** Does an existing element truly perform the task, or have you merely renamed the old performer?

## 5. Attribute Dependency — create a new dependency

**Recipe:** Pick two variables that are currently independent (often internal vs external). Create a dependency where one controls the other — add, strengthen, break, or reverse it.

**Prompt:** "If X changed with Y — when Y moves, X must move — what rule would make the dependency valuable?"

**Example:** Time-to-first-value depends on invite source — invited users skip the tour entirely, solo users get the checklist. Prior dependency: none.

**Check:** Were the variables independent before? If they already covary, pick another pair.

## After the virtual product

Each virtual product is followed by enrichment: add the minimal feasible fix that restores value while staying closed-world. Record the change, the new benefit, and the test.
