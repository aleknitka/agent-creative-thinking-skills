# Constraints — Catalog and Selection

A forcing constraint is not a real limit; it is a design move that blocks the generic answer. Keep it tight enough that the obvious path disappears.

## Constraint families

- **No interface:** no screen, no form, no dashboard — how would value be delivered invisibly or through an existing surface?
- **No budget / no team:** no new headcount, no new code — how would the problem be solved by rearranging what exists?
- **No time:** one day, one hour — how would it ship if the window were fixed?
- **Offline-only / solo-only / peer-only:** who is removed, and what must compensate?
- **10× cheaper / 10× fewer users:** what scales differently at the extreme?
- **Most constrained user first:** design for the lowest-resource segment and let it pull the middle.

## Selection

- Pick 2–3 constraints that each block a different generic category (interface, effort, time).
- Avoid constraints that reproduce the same forcing ("no email" vs "no chat" both block async messaging — vary the axis).
- Timebox generation per constraint; transfer comes after all are explored.
